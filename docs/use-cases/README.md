# 📋 مستندات جامع Use Case های سیستم پذیرش

این مستند شامل تشریح کامل تمامی Use Case های سیستم پذیرش است که به صورت دسته‌بندی شده و با جزئیات کامل ارائه گردیده است.

## 🎯 درباره این مستند

این مستند به منظور تشریح کامل منطق و عملکرد هر یک از Use Case های سیستم تهیه شده است. در این مستند:

- تمامی **Features** سیستم به صورت دسته‌بندی شده معرفی می‌شوند
- هر **Command** و **Query** با توضیحات کامل شرح داده می‌شود
- منطق پشت هر Use Case تشریح می‌گردد
- **سرویس‌های سیستم** و وظایف آن‌ها معرفی می‌شوند

**توجه:** این مستند شامل جزئیات امنیتی (AuthN/AuthZ) نمی‌باشد. برای اطلاعات امنیتی به مستندات مربوطه مراجعه کنید.

---

## 📚 ساختار کلی سیستم

سیستم پذیرش بر اساس معماری **Clean Architecture** و الگوی **CQRS (Command Query Responsibility Segregation)** پیاده‌سازی شده است:

- **Commands**: عملیات تغییر دهنده که وضعیت سیستم را تغییر می‌دهند (Create, Update, Delete)
- **Queries**: عملیات خواندن داده که تنها اطلاعات را دریافت می‌کنند (Read)
- **Services**: سرویس‌های کمکی که وظایف خاصی مانند ارتباط با وب سرویس‌ها، مدیریت کش و غیره را بر عهده دارند

### 1️⃣ مدیریت دانشجو (Student Management)

این دسته شامل تمامی Use Case های مربوط به مدیریت اطلاعات دانشجویان (طلاب) می‌باشد.

#### 1.1 مدیریت اطلاعات شناسنامه‌ای

**منطق کلی:**
- دریافت و به‌روزرسانی اطلاعات شناسنامه‌ای دانشجو از طریق وب سرویس ثبت احوال
- اعتبارسنجی کد ملی و تاریخ تولد
- همگام‌سازی اطلاعات شناسنامه‌ای با سامانه‌های خارجی

**Use Case ها:**
- `UpdateStudentBirthCertCommand`: به‌روزرسانی اطلاعات شناسنامه‌ای دانشجو
  - اعتبارسنجی کد ملی و تاریخ تولد از طریق وب سرویس ثبت احوال
  - بررسی تکراری نبودن کد ملی
  - کنترل دسترسی برای تغییر کد ملی و تاریخ تولد (فقط کاربران ارشد)
  
- `SyncStudentBirthCertCommand`: همگام‌سازی خودکار اطلاعات شناسنامه‌ای
  - دریافت اطلاعات از وب سرویس
  - به‌روزرسانی خودکار اطلاعات موجود
  
- `UpdateStudentProfilePictureCommand`: به‌روزرسانی تصویر پروفایل
  - دریافت تصویر از ثبت احوال
  - ذخیره تصویر در سیستم
  - ثبت تاریخچه تغییرات تصویر

#### 1.2 مدیریت پرونده دانشجو

**منطق کلی:**
- مدیریت وضعیت پرونده دانشجو (فعال/غیرفعال)
- تمدید پرونده
- بلوک و رفع بلوک پرونده

**Use Case ها:**
- `StudentExtensionCaseCommand`: تمدید پرونده دانشجو
  - بررسی شرایط تمدید
  - محاسبه تاریخ انقضای جدید
  - ثبت تاریخچه تمدید

- `ManualStudentExtensionCaseCommand`: تمدید دستی پرونده (توسط کارمند)
  - نیازمند مجوز خاص
  - امکان تعیین تاریخ دلخواه

#### 1.3 مدیریت تحت تکفل دانشجو

**منطق کلی:**
- مدیریت افراد تحت تکفل دانشجو (همسر، فرزندان)
- ثبت و به‌روزرسانی اطلاعات شناسنامه‌ای تحت تکفل‌ها
- اعتبارسنجی روابط خانوادگی

**Use Case ها:**
- `UpdateDependentBirthCertCommand`: به‌روزرسانی اطلاعات شناسنامه‌ای تحت تکفل
- `SyncDependentBirthCertCommand`: همگام‌سازی اطلاعات تحت تکفل
- اعتبارسنجی رابطه با دانشجو از طریق وب سرویس

#### 1.4 مدیریت اطلاعات تماس

این سرویس‌ها برای ارتباط با وب سرویس‌های سازمان ثبت احوال و سایر سامانه‌های دولتی استفاده می‌شوند:

- `ValidateParentChildRelationship`: اعتبارسنجی رابطه والد-فرزند

#### سرویس‌های اعتبارسنجی مالی
- `ValidateShebaOwnerShip`: اعتبارسنجی مالکیت شماره شبا

### سرویس‌های مدیریت درخواست (Request Services)

این سرویس‌ها برای مدیریت درخواست‌های تغییر اطلاعات استفاده می‌شوند:

- `Create`: ایجاد درخواست جدید
- `Get`: دریافت اطلاعات درخواست
- `SendCommand`: ارسال درخواست برای بررسی
- `ApproveRequestByEmployee`: تایید درخواست توسط کارمند
- `ApproveRequestByStudent`: تایید درخواست توسط دانشجو
- `GetEmployeeRequestsToApprove`: دریافت درخواست‌های در انتظار تایید
- `GetRequestComparisonDetailAsync`: مقایسه تغییرات درخواست شده

**منطق کاری:**
1. دانشجو درخواست تغییر اطلاعات را ثبت می‌کند
2. درخواست به کارمند مربوطه ارسال می‌شود
3. کارمند درخواست را بررسی و تایید/رد می‌کند
4. در صورت تایید، تغییرات اعمال می‌شوند

### سرویس‌های پردازش پس‌زمینه (Background Services)

- `SyncPermissionsBackgroundService`: همگام‌سازی دسترسی‌ها به صورت دوره‌ای

## 🎯 الگوهای طراحی و معماری

### CQRS Pattern
تمامی Use Case ها به دو دسته تقسیم می‌شوند:
- **Commands**: عملیات نوشتن که وضعیت را تغییر می‌دهند
- **Queries**: عملیات خواندن که فقط داده بازمی‌گردانند

### Repository Pattern
دسترسی به داده‌ها از طریق Repository ها انجام می‌شود که لایه انتزاع بین منطق کسب‌وکار و داده است.

### Mediator Pattern
استفاده از MediatR برای جداسازی درخواست‌ها و پردازشگرهای آن‌ها.

### Validation Pattern
استفاده از FluentValidation برای اعتبارسنجی ورودی‌ها.

## 📝 نکات مهم

1. **اعتبارسنجی چندلایه**: تمامی داده‌های ورودی در چند سطح اعتبارسنجی می‌شوند
2. **استفاده از وب سرویس‌ها**: بسیاری از اطلاعات از وب سرویس‌های خارجی دریافت و اعتبارسنجی می‌شوند
3. **سیستم درخواست**: تغییرات حساس نیازمند ثبت درخواست و تایید هستند
4. **Audit Log**: تمامی تغییرات در سیستم ثبت و قابل پیگیری هستند
5. **کش**: داده‌های پرتکرار در کش ذخیره می‌شوند برای بهبود عملکرد
